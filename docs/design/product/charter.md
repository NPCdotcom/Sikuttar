## 1. 一行説明

愚痴感覚で失敗談を投稿し、他人の失敗から学べる——投稿と適切な表示の両方を重視した、失敗談共有＋RAG の Web アプリ。

> NPC: 失敗談を共有するツイートのようなものにRAG機能をMix。愚痴感覚で投稿し、他人の失敗から学ぶことを重視。投稿と適切な表示の両方を重視。

## 2. 背景・動機

実務上の動機:

- 自分の失敗談を気軽に共有でき、同時に他人の失敗談を参照できる場が欲しい。
- 共同開発などでは「失敗が許容される」風潮が必要で、それはプログラミング以外にも通じる。

その背景にある考え:

- 失敗から得られる学びは成功のための財産だが、その学びは自分の失敗だけから得る必要はない（rako）。
- 他人の失敗から学ぶことで、新たな失敗を防ぎ、より良い行動につなげられる。
- だから、愚痴感覚で投稿でき、かつ他者の参考になるアプリが欲しい。

まとめ:

**「失敗無き学習は、失敗を防ぐことに寄与しない。」**

## 3. 誰のためのものか（利用者）

| 利用者 | 主な目的・状況 | 優先度（高/中/低） |
|--------|----------------|--------------------|
| 開発者（初期スコープ） | 愚痴感覚で失敗談を残し、他開発者の失敗から学ぶ | 高 |
| 失敗を共有したい人／他人の失敗から学びたい人（将来） | 職種を問わない利用 | 低（期日トレードオフで当面スコープ外） |

非利用者（対象外）:

- 悪意ある第三者（荒らし・攻撃的ダメ出し・情報の悪用など）

表示・モデレーションの方向:

- 一定の反応が付かない投稿は表示優先度を下げる（集合知の質を守る）。
- 優先度の枠組み: **ベイズ平均**（評価が少ない投稿に全体平均を反映）＋**指数減退**（経過時間）（rako）。
- リアクション種別ごとに意味が違うため、**何を切り出すかで重みづけが変わる**（詳細パラメータは要件／設計側）。
- 「BAD」系シグナルは **システム内部の参考** に留め、人間向けの公開ランキングにはしない。具体的な数値は載せない。投稿者のプロフィール等に載る自分の投稿には BAD を載せない。

## 4. 目的・非目的

| 目的（やること） | 非目的（やらないこと） |
|------------------|------------------------|
| 失敗談を気軽に共有できる（愚痴感覚の投稿） | 他人の失敗談へのダメ出し・糾弾・論破の場にすること |
| 原因や状況を任意で残せる（必須にしない） | 成功自慢・一般 SNS の全方位タイムライン化 |
| 他人の失敗が「適切に」見つかる・表示される（RAG は段階導入） | 心理安全性を下げる公開評価競争（いいね数至上・BAD 数の可視化など） |
| 限定リアクションで共感・有用さの軸を分けて示せる | 自由記述の批判コメント中心の議論スレ |
| 表示上の匿名性を保ちつつ、アカウント属性は内部保持 | 身元晒しや実名必須の失敗告白 |

匿名・アカウント方針:

- アカウント情報（職業・専門分野など）は DB に持つが、**表示しない**ことで匿名性を保つ。
- 将来職種横断する際は、最低限の所属ラベル表示（例: 「名無しの〇〇」系）を検討しうるが、既存掲示板の丸パクリは避ける（参考に留める）。

限定リアクション（確定セット）:

| リアクション | 意味（共同者合意の方向） | 重み・後段利用のヒント |
|--------------|--------------------------|------------------------|
| わかる | 内容全体が、他者の経験と類似しているときに増える | 類似性・全体マッチの信号。RAG の類似提示にも応用しうる |
| 参考になる | 原因などに着目して増える想定 | 原因・学びどころへの有用さの信号。切り出し方で重みが変わる |

- 原因フィールドは **任意**（愚痴の気軽さ維持 · rako）。

## 5. 成果物のイメージ

| 観点 | 想定 |
|------|------|
| 利用者から見える形 | ブラウザ上の Web アプリ。短文〜中文の失敗談タイムライン／フィード |
| 主な入出力 | 入力: 失敗談投稿（状況・原因は任意）· 「わかる」「参考になる」·（後段）検索／類似照会。出力: 投稿一覧 ·（後段）関連する他人の失敗談 |
| 「動いた」と言える最小状態（MVP） | **投稿・閲覧**ができること。類似提示（RAG）は投稿基盤のあと／余裕があれば |

## 6. 成功の目安

成功:

- 発表時点（§7）で、少なくとも投稿→閲覧が一続きで動く。余裕があれば関連失敗の提示まで。
- 利用者が「ダメ出しされない」と感じられる範囲の体験（限定リアクション・非難禁止・BAD 非可視化）。
- 中途半端な見た目の完成より、拡張しやすい骨格と動く最小価値が残っている。
- 共同開発者向けに、ドキュメント・Issue・ブランチ／PR を同期できるハーネスが GitHub 上で固まっている（着手の前提）。

失敗・避けたい状態:

- 批判・晒し・荒らしが主用途になる。
- 発表に間に合わせるため、拡張不能な継ぎはぎ実装だけが残る。
- 投稿はあるが「他人の失敗が役立つ形で出てこない」（表示・検索が機能しない）——RAG 段階では特に。

## 7. 制約・前提

| 種類 | 内容 |
|------|------|
| 技術・言語・ランタイム | TypeScript。フロント React。API Hono（Assumption · 共同者提示） |
| プラットフォーム | 開発: Cloudflare 前提の Web（Assumption） / 利用: ブラウザ（Fact · §0） |
| 期間・マイルストーン感 | 約 2 週間。発表 2026-10-25。最低限の動くものは必須だが、拙速な中途半端完成は避ける |
| 法務・ライセンス・公開範囲 | **パブリック**（ハッカソン作品）。ライセンス文面は charter 上 **具体的に明記しない** |
| 依存する外部サービス | Cloudflare（RAG 等を含む想定 · Assumption） |
| 共同作業基盤 | GitHub（パブリック）。Issue 駆動を想定 |

共同開発の進め方（Assumption · 製品要素ではない）:

- アジャイルな短いサイクルで進める。
- エージェント向けドキュメントとプログラミング構造の両方で縛る。
- 設計スタンス: メッセージ駆動・関数の追加による拡張を優先。クラス中心 OOP は必須としない。開放閉鎖（拡張に寛容）を意識する。
- 関数型／OCP 寄りの構造は、ローカルのグローバル知識にある設計思想を参照する（実装チャット側で適用）。
- Issue 駆動なら、**ドキュメント・Issue・ブランチ・PR を適切に同期するハーネス**が必要（整備作業は本チャット外）。

## 8. 主要要素（名前だけ · のち H1）

製品として名前を付ける単位（認識オブジェクト候補）:

- 失敗談（投稿）
- フィード／タイムライン
- 限定リアクション（わかる / 参考になる）
- BAD シグナル（非表示・システム用）
- 表示優先度（ベイズ平均＋時間減退 · リアクション種別の重み）

- アカウント属性（内部保持 · 非表示）

## 9. 参考・類似・差別化（任意）

| 参考・競合・類似 | 取りたい点 | 避けたい点 |
|------------------|------------|------------|
| Twitter / X 的な短文投稿 | 愚痴感覚の気軽さ、投稿の手軽さ | 議論・炎上・全方位タイムライン化 |
| 一般的な Q&A / 知恵袋 | 他者経験からの学び | 正誤判定・ダメ出し文化 |
| （集合知コミュニティ一般） | 失敗談の集積による集合知 | 成功談中心・自慢競争 |
| 匿名掲示板の属性ラベル | 「名無しの〇〇」的な最小所属（将来検討の参考） | 既存サービスの丸パクリ |

差別化の芯: **失敗談を中心に投稿・集積し、より強固な集合知の形成を目指す。**
