# 要件定義 — 失敗談共有（failure-share）

親: [要求.md](./要求.md)（agreed · 2026-10-15）

## スコープ

### In scope

- MVP（R1–R4）の検証可能な振る舞い
- should（R5–R7, R10–R11）の受け入れ条件（実装順は後段可）
- could（R8–R9）は枠のみ・パラメータは Open

### Out of scope

- 職種横断の本格展開
- 自由記述の批判コメントスレ
- BAD の公開数値・公開ランキング
- ハーネス整備（docs/Issue/branch/PR 同期 · 別作業）
- 重み係数・ベイズ／減退の最終式の確定（設計実験へ）

## 機能要件

| ID | 要件 | 対応要求 | 優先 | 検証方法 |
|----|------|----------|------|----------|
| FR1 | 利用者はブラウザから失敗談本文を投稿でき、永続化される | R1 | must | 手動: 投稿 → 再読込後も一覧に存在する |
| FR2 | 投稿一覧（フィード／タイムライン）をブラウザで閲覧できる | R2 | must | 手動: 複数投稿が時系列または既定順で見える |
| FR3 | 投稿フローで状況・原因は未入力のままでも投稿完了できる | R3 | must | 手動: 本文のみで投稿成功。任意フィールドを空でもエラーにしない |
| FR4 | 一覧・詳細の表示に、投稿者の実名・身元を特定するラベルを出さない（初期） | R4 | must | 手動/UI: 表示上に氏名・ログインID等が出ないことを確認 |
| FR5 | リアクション種別は「わかる」「参考になる」の2種に限定して付与できる | R5 | should | 手動: 両種が付与でき、それ以外の自由テキスト反応UIが無い |
| FR6 | 投稿に対する自由記述の批判コメント機能を提供しない（MVP〜発表スコープ） | R6 | should | レビュー: コメント入力UIが無い／無効である |
| FR7 | BAD シグナルを付与する場合でも、公開UIに件数・ランキングとして表示しない。プロフィール上の自分の投稿にも BAD を載せない | R7 | should | 手動/レビュー: 公開画面・プロフィールに BAD 数値なし |
| FR8 | アカウント属性（職業等）を保持できるデータ項目があり、初期UIでは表示しない | R10 | should | レビュー: スキーマまたは内部モデルに属性欄あり、一覧UIに非表示 |
| FR9 | 表示優先度にベイズ平均＋時間減退＋種別重みの枠を置ける拡張点がある（式の値は仮で可） | R8 | could | 設計/コードレビュー: 優先度計算の差し込み点がある。係数は定数仮置き可 |
| FR10 | 蓄積投稿から関連失敗を提示する導線またはAPI境界を定義できる（本実装は後段可） | R9 | could | 設計レビュー: 類似提示の入口が文書化されている |

## 非機能要件

| ID | 要件 | 対応要求 | 優先 | 検証方法 |
|----|------|----------|------|----------|
| NFR1 | 配布形態は Web。追加のネイティブアプリを必須としない | R1–R2 | must | レビュー: 利用手順がブラウザのみ |
| NFR2 | 発表用MVPは「投稿→閲覧」が一続きでデモ可能 | R1–R2 | must | 手動デモ: 投稿直後に一覧で確認できる |
| NFR3 | モジュール／関数追加で拡張しやすい境界を保つ（継ぎはぎ単体で終わらせない） | R11 | should | 設計レビュー: 投稿・一覧・リアクションが分離可能な単位になっている |
| NFR4 | 想定スタック（TS / React / Hono / Cloudflare）から外れる場合は ADR で記録する | — | should | 差分時に ADR 有無を確認 |

## 受け入れ（ゲート用まとめ）

**P2 → P3 に進む条件**

1. must の FR1–FR4 · NFR1–NFR2 が Open なしで合意されている
2. should / could の未確定パラメータ（係数・式）は Open に残り、ブロッカーでないと明記されている
3. 基本設計（P3）へ渡す認識オブジェクト一覧が **charter §8** と一致している

## 設計への制約（ユーザー合意 · 2026-10-15）

P3 以降の設計は次に従う（独自の並行分類を立てない）:

1. **認識単位の骨格** = charter §8（失敗談 · フィード · 限定リアクション · BAD · 表示優先度 · 関連失敗提示 · アカウント属性 · 匿名表示）
2. **着手順** = charter 着手順 1→4（投稿閲覧 → リアクション／体験ガード → RAG → 表示優先度）
3. **設計スタンス** = charter §7（メッセージ駆動 · 関数追加による拡張 · クラス中心 OOP は必須としない）
4. スタック名は製品語彙に混ぜない（§7 側）

## エージェント提案（実装方針のたたき）

| 案 | 概要 | 向く状況 |
|----|------|----------|
| 1（推奨） | 先に FR1–FR4 だけを満たす縦スライス → 次に FR5–FR7 | 2週間・MVP優先 |
| 2 | FR1–FR7 を同時に仕様固定してから実装 | 体験ガードを最初から揃えたいが工期リスク大 |
| 3 | FR1–FR2 のみ先にコード化し、FR3–FR4 は後付け | 最短だが匿名・任意入力が後回しになりやすい |

**推奨: 1** — 要求の must/should 分離と charter 着手順に一致。

**決定（2026-10-15）**: 要件 agreed · 実装方針案1 · 設計は charter 構造に従う。
